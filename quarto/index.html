    Quarto documents

    Quarto is a document publishing system and literate programming tool that allows you to execute code inside documents, e.g., for doing calculations, creating figures, etc. Because it might be unintuitive to write heavy data processing or simulation code into a document, Calkit enables those steps to be done with other kinds of pipeline stages that reproducibly integrate and feed a Quarto stage derived artifacts like reduced datasets, results, or figures, so that cheap calculations and transformations can stay in Quarto.

    A quarto stage renders a Quarto document, .qmd or .ipynb, in one of the project's environments:

    pipeline:
  stages:
    report:
      kind: quarto
      target_path: index.ipynb
      environment: main
      args: [--execute]

    Which Quarto is used?

    Quarto is part of a stage's environment, like any other tool a stage runs, so a document renders with the same version on every machine: add quarto to a Conda or Pixi environment, or quarto-cli to a uv or pip one. The stage renders with calkit quarto render, which checks that the environment has it included, i.e., that it's not actually on the path from a system-wide install, and fails rather than quietly using whatever version is installed on the machine. To use Quarto installed outside an environment on purpose, list it in the project's requirements:

    requirements:
  - quarto

    Notebooks

    Rendering a notebook with --execute writes its outputs back into it, which is what a site built from it shows. The stage depends on the notebook with its outputs stripped, as a notebook stage does, so re-running cells interactively doesn't make it out of date, while editing a cell's code or prose does. Without --execute, Quarto shows the outputs saved in the notebook, so the stage depends on them too.

    Values from the pipeline

    A document can show values from a results file written by another stage with the ckvalue shortcode, which reads like its Markdown and LaTeX counterparts: a results file, or the name of a declared result, a key, and optionally a Python format spec, positionally or by name.

    The RMS is {{< ckvalue results/metrics.json rms .3f >}}
over {{< ckvalue results/metrics.json key=fit.n >}} samples.

    Paths are relative to the project. Results files can be JSON, YAML, or TOML, and keys are separated by dots to reach into nested values. Formats take a sign, a , or _ separator, and a precision and type, e.g., .2f, ,d, or .1%, or a template, e.g., {value:.1f} m/s. The results files are inputs to the stage, so a change to a value renders the document again.

    A value quoted from a reference is shown with {{< ckrefval citation-key name format >}}, from what calkit.yaml records for the reference. See quoting values from references.

    To show a value saved from a notebook cell, use the notebook's path instead of a results file, e.g., {{< ckvalue fit.ipynb k_25 .3f >}}. See saving values from cells for more info.

    calkit check repro -c numbers lists numbers typed into a Quarto document that has a stage, including a notebook's Markdown cells, that look like results but have nothing recorded behind them, so they can be read from the pipeline instead. Numbers in shortcodes, inline expressions, and code are left out, as is a line with a <!-- calkit: ignore --> comment.

    When the pipeline is compiled, Calkit writes the shortcode as a Quarto extension in _extensions/calkit/, in the Quarto project's folder, i.e., where _quarto.yml is, or beside the document if there isn't one, so documents can use it without listing it. It reads each value from its results file when the document renders, so with the extension kept in Git, the document renders the same without Calkit, e.g., when a site is published by quarto publish, as long as its results files are on this machine. Before the stage renders, Calkit checks each value can be shown, naming the line of any that can't.

    A document that runs code can also show values with Quarto's inline expressions, e.g., `{python} f"{rms:.3f}"`, but then its results files have to be listed as the stage's inputs, and Calkit can't trace the numbers back to them.

    A figure or table from a notebook can go in another document with Quarto's embed shortcode, e.g., {{< embed analysis.ipynb#fig-decay >}}, which shows the output saved in the notebook for the cell with that label. The notebook is an input to the document's stage, and if another stage renders it with --execute, the document renders after that stage.

    See examples/quarto for a project that does all of these: a Julia simulation, a Python notebook that fits it, and an R report that shows values from each and the notebook's figure.
